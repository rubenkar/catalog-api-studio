# Оцифровка PDF-каталогов подшипников → JSON

**Дата:** 2026-08-15
**Статус:** утверждено (диалог 2026-08-15)

## Миссия и границы

Автономный конвейер: PDF-каталог поставщика подшипников → один JSON-файл со
структурированными записями. Заливка в БД stockshop и любая дальнейшая обработка —
задача другого приложения, **вне рамок этого проекта**.

- Вход: PDF-каталоги из `data/uploads/` (ASAHI, Dinroll, FBJ, FLT, KOYO, KSM, LYC, NACHI, NSK).
- Выход: `output/bearings/<brand>.json` + `output/bearings/<brand>.manifest.json`.
- Запуск: CLI, без участия PySide6 UI. UI-наработки (детекция таблиц/линий) используются
  как библиотека там, где нужны (сетка таблиц для отпечатка layout).

## Ключевой принцип: LLM понимает структуру, механика извлекает данные

LLM (DeepSeek, подписка есть, ключ `DEEPSEEK_API_KEY` в `C:\!dev\markagent\.env`)
применяется для определения паттерна данных, layout-а страницы и структуры таблиц —
**не** для построчного извлечения каждой страницы. Механическое извлечение по
выведенным правилам — детерминированное, бесплатное, воспроизводимое.
DeepSeek API — только текст (без vision): LLM получает layout-сохраняющий текст
страниц из PyMuPDF, не изображения.

## Схема выходных данных

Состав полей **индивидуален для каждого каталога** — определяется тем, какие
характеристики публикует производитель. Всегда присутствует глобальное ядро:
`designation` (обозначение), `type` (тип подшипника), основные размеры, `page`.

### Манифест полей (`<brand>.manifest.json`)

Составляется этапом профилирования, может быть отредактирован вручную перед
извлечением:

```json
{
  "source": "KOYO - Ball and Roller Bearings.pdf",
  "brand": "KOYO",
  "fields": [
    { "key": "designation", "label": "Bearing number", "unit": null,  "core": true },
    { "key": "type",        "label": "Bearing type",   "unit": null,  "core": true },
    { "key": "d",           "label": "Bore diameter",  "unit": "mm",  "core": true },
    { "key": "D",           "label": "Outer diameter", "unit": "mm",  "core": true },
    { "key": "B",           "label": "Width",          "unit": "mm",  "core": true },
    { "key": "Cr",          "label": "Dynamic load rating", "unit": "kN" },
    { "key": "grease_rpm",  "label": "Limiting speed (grease)", "unit": "rpm" }
  ]
}
```

### Данные (`<brand>.json`)

```json
{
  "source": "KOYO - Ball and Roller Bearings.pdf",
  "brand": "KOYO",
  "extracted_at": "2026-08-15T12:00:00Z",
  "pipeline_version": "1.0",
  "items": [
    { "designation": "6205-2RS", "type": "deep_groove_ball",
      "d": 25.0, "D": 52.0, "B": 15.0, "Cr": 14.0, "grease_rpm": 12000,
      "page": 143 }
  ],
  "stats": { "pages_total": 1084, "pages_with_data": 412, "items_count": 8734 },
  "issues": [ { "page": 217, "problem": "правило разбора не сработало" } ]
}
```

Правила значений: числа — числа в единицах манифеста (LLM/парсер конвертируют);
неизвестное → `null`, не выдумывается; каждая запись несёт `page` для ручной сверки.

## Конвейер

1. **Профилирование** (LLM, один раз на каталог) — по выборке страниц (равномерная
   выборка ~10–15 страниц из числа прошедших фильтр числовой плотности): манифест
   полей + перечень встречающихся типов layout.
2. **Кластеризация страниц** (детерминированно) — структурный «отпечаток» страницы:
   расположение текстовых блоков/колонок, сетка таблиц (существующая детекция линий
   как библиотека). Страницы с одинаковым отпечатком → один кластер. Страницы без
   табличных данных (обложки, вводные главы) отсеиваются эвристикой числовой
   плотности; сомнительные не отбрасываются, а идут в кластер «прочее».
3. **Правило разбора на кластер** (LLM, один раз на тип layout) — по 1–2 образцовым
   страницам: где таблица, соответствие колонок полям манифеста (по x-координатам),
   устройство строк, объединённые ячейки, продолжения таблиц, наследование значений
   (например, размер ряда указывается один раз на группу строк).
4. **Механическое извлечение** (без LLM) — правило применяется ко всем страницам
   кластера: слова PyMuPDF раскладываются по колонкам детерминированно.
5. **Валидация + fallback** — Pydantic: числа парсятся, d < D, designation непустой.
   Брак страницы → повторный точечный запрос LLM по этой странице (уточнить правило
   или извлечь напрямую). Повторный провал → страница в `issues`.
6. **Сборка** — дедупликация по `designation` (слияние записей одной модели из разных
   таблиц), итоговый JSON + `stats` + `issues`.

Все ответы LLM кэшируются на диске (`cache/<pdf>/…`); прерванный прогон возобновляется
без повторных трат; `--force` пересчитывает. Ожидаемый объём LLM-вызовов — десятки на
каталог (профиль + правила + fallback), не тысячи.

## Структура кода

Новый подпакет `app/extraction/bearings/` (существующий `app/extraction/pipeline.py` —
стаб, не трогаем):

- `cli.py` — точка входа `python -m app.extraction.bearings …`
- `profiler.py` — этап 1 (манифест, типы layout)
- `fingerprint.py` — этап 2 (отпечаток страницы, кластеризация, отсев нетабличных)
- `rules.py` — этап 3 (запрос и представление правил разбора)
- `mechanics.py` — этап 4 (детерминированная раскладка слов по правилу)
- `validate.py` — этап 5 (Pydantic-модели, sanity-проверки)
- `assemble.py` — этап 6 (дедупликация, сборка файла)
- `llm.py` — клиент DeepSeek (OpenAI-совместимый API, JSON-режим, ретраи, кэш)
- `pagetext.py` — layout-сохраняющий текст страницы из PyMuPDF-слов

### CLI

```
python -m app.extraction.bearings profile "data/uploads/KOYO*.pdf"   # → manifest
python -m app.extraction.bearings extract "data/uploads/KOYO*.pdf"   # → json
```

Ключ API: из окружения `DEEPSEEK_API_KEY`, фолбэк — чтение `C:\!dev\markagent\.env`.

## Обработка ошибок

- Ошибки LLM API: ретраи с бэкоффом; невалидный JSON от LLM — повторный запрос с
  указанием ошибки; после 3 попыток — страница/этап в `issues`, конвейер не падает.
- Ошибки валидации: на уровне записи — запись отбрасывается с фиксацией в `issues`;
  на уровне страницы (доля брака выше порога) — страница уходит в fallback.
- Конвейер всегда доводит каталог до конца и пишет честные `stats`/`issues`.

## Тестирование

- Юнит-тесты: layout-текст, отпечаток/кластеризация, механическая раскладка по
  фиксированному правилу, валидация, дедупликация — на маленьких фикстурах.
- Интеграционный тест: 2–3 реальные страницы KOYO с записанными (mock) ответами LLM —
  полный проход без сети.
- Приёмка: живой прогон одного малого каталога (KSM или Dinroll), ручная сверка
  выборки записей со страницами PDF.

## Вне рамок

- Заливка в stockshop, сопоставление с существующей БД, ценообразование.
- Мебельные каталоги (`catalogs/`, 50 поставщиков) — следующий этап после отладки
  конвейера на подшипниках; конвейер проектируется так, чтобы смена домена
  означала смену промптов профилирования и ядра полей, не переписывание механики.
- OCR битмапных каталогов (текущие каталоги подшипников — текстовые PDF); при
  необходимости добавится PaddleOCR перед этапом 2.
